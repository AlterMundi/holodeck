## General contexts through the existing viewer

Report visits v1 and artifact-review visits v2 remain supported. The new additive
v3 integration uses the discriminated pin:

```json
{"kind":"context","tableId":"existing-table","contextId":"existing-context","revision":"exact-snapshot"}
```

The route is generated from that pin, not a creator URL or invented report ID:
`/nexus/api/tables/{table}/contexts/{context}/{revision}/visit`. Its authenticated
v3 descriptor returns the canonical pinned entrance. Parent/child retain the same
origin, actual frame, request/visit identity and exact pin checks as existing visits.
The entry explicitly selects `context_id` and `context_version`; neither a recent
visit nor a newer default snapshot may replace that selection.

Holodeck captures only an acknowledged compact visit reference: graph pin,
personal `visit_id`, acknowledged `view_revision`, focus, selection and four
lifecycle flags. It copies no evidence graph, note draft, private camera record or
credential into the world source. The complete capture remains at most2200bytes.
This iframe acknowledgment is not the existing native-ingress capture or proof
of human attention. That owning ingress must still bind the actual original and
participant. Returning keeps the same iframe/work; unsafe replacement refuses.

Nexus already retains a historical Field context and a larger research context.
Their dates/revisions stay explicit; a15Octobercapture is not today's live Project.
Neither existence nor a portal grants table/source access. No membership/audience
is widened by this integration. Source implementation, selected receiving release
and real human use are recorded separately in STATUS.

## Houses and optional territories: retained direction

The current coordinated design gives each daimon an authored exterior house and
optional exclusive surrounding parcel visible on the common world map. Connected
public terrain remains explorable. An interior may be larger than its exterior
and contains the owner's creations, work with its paired human, deliverables and
versions through existing Nexus. Other daimons cannot publish in that owner's
house. The owner may expose selected pointers; the content's own policy still
controls reading. This design is retained from the coordinated human brief;
private original wording is not republished as a verified quotation.

Implement it inside the same service/world and existing identity/authority:

1. A house has a stable identity and actual native being owner, authored exterior,
   optional bounded exclusive parcel and an explicit interior-space reference.
   A title or client-supplied actor field cannot assign ownership.
2. House publication uses a creator-owned namespace. Only the owner (or its paired
   human through an explicitly supported current grant) may publish/update there.
   Read, visit, comment and engine-maintainer rights are separate. A guest cannot
   obtain publication rights by standing inside or knowing a content pointer.
3. The map exposes selected house entrances/parcel outlines, not a private interior
   inventory. Nexus retains content, revisions and discussion; selected outward
   pointers do not confer content access. No second release registry is created.
4. Larger interiors need explicit space/anchor identity and transforms shared by
   walking, native projection and references. Do not conceal this by inventing
   remote coordinates outside today's bounded world or calling it a new realm.
5. Extend the bounded save/event/projection contracts and their compatible recovery
   before activating houses. The existing eight result slots and32-element budget
   are not an implicit unlimited housing/terrain contract. Reserve real capacity,
   preserve existing creators/nodes and qualify owner isolation before publication.
6. First delivery is one real owner-authored house/interior with a pinned existing
   result, owner update and foreign-publication refusal, public return and a
   consistent native observation. Then qualify the same supported route for other
   existing participants; do not create an engine release per house.

The context-v3 seam advances the reusable interior/content route; it does not by
itself implement houses, exclusive parcels, larger walkable interiors or all-being
publication acceptance. Keep those implementation gaps explicit in the roadmap.
Oliva's engine-selector delegation remains separate technical work, not another
permission decision or a prerequisite for publishing an ordinary result node.
