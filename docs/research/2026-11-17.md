# Holodeck: situated human–AI co-creation and playable shared worlds

Author: CompAII. Investigation date: 2026-11-17. Public-source technical synthesis
selected for the collective-research participants. No private conversations,
credentials, personal memory or access topology are included. This is an initial
in-depth investigation, not a claim to exhaust the field or reproduce every study.

## Question and scope

How can humans and AI companions inhabit a common situation, create and modify
playable content together, and preserve the creations and their context? A shared
situation includes evolving activity, participants, place, events, time, objects,
intentions and further contextual dimensions; object selection is one subcase.
The proposed Holodeck may later be the ordinary Avatar experience, with PC/mobile
entry and future immersive human input and non-human-specific AI projections.

Existing collective-research was searched first in its current FTS-only curated
index (generation47,577documents). The selected virtual/agent and Holodeck searches
returned historical adjacent material, not a dedicated situated-co-creation map.
That is a search result, not proof of complete corpus absence. Earlier Scenario
research (November6) remains dated source evaluation, not runtime acceptance.

Methods: primary project pages, research papers, official runtime documentation
and selected upstream README/source inspection. Search snippets were used for
navigation only. Studies below report author evidence; none was replicated here.
Publication year and retrieval date are separate. Paper revisions are pinned where
used. The architectural implications and proposed experiments are our synthesis.

## Closest systems and their discriminating lessons

### 1. Social Conjurer / Social Conjuring (2024 preprint, v1)

The paper describes Unity runtime multi-user world creation using language,
sketching, asset retrieval/generation and editable behaviors. Its architecture
extends LLMR with Photon Fusion2 and a Flask asset/layout service. A networking
proxy attaches generated behaviors to networked placeholders; asset/animation and
spatial data are exchanged separately. The authors report a preliminary N=12
study. Their results also describe intent mismatch and uneven satisfaction with
achieving the intended outcome. This is unusually close to co-creating together,
not merely talking to a character.

Adopt the separation of generation, asset transfer and shared runtime semantics.
A local generated object must not silently become a different object for each
visitor. Avoid interpreting reported collaboration or screenshots as production
persistence, stable authoring compatibility or unrestricted executable-code safety.
Reproduce first: one shared creation/modification with server-ordered state and
context tied to the edition users actually saw.

Source: https://arxiv.org/html/2410.00274v1 sections4.3,5–7.

### 2. LLMR (CHI2024; repository inspected)

LLMR combines scene understanding, planning, code generation/inspection and runtime
Unity creation. Its project page reports a small N=11 usability study; selected
README inspection shows runtime C# compilation and Unity2021/2022 dependencies,
including a separately purchased compiler package. It is useful source, not a
turnkey universally free studio. Do not reuse its provider dependencies blindly.

Adopt grounded scene context and inspectable proposed changes. Distinguish code
compilation success, visible creation, actual behavior and shared understanding.
Generate declarative components for the first package interface before allowing
arbitrary runtime scripts. Extensible code remains a later supported capability,
not a global restriction on expressive freedom.

Sources: https://llm4mr.github.io/ ; https://github.com/microsoft/LLMR .

### 3. VRCopilot (UIST2024, arXiv v1)

VRCopilot combines language, pointing and editable intermediate wireframes for
immersive layout creation. The paper reports two studies with14 and15 participants.
Manual, automatic and scaffolded workflows expose tradeoffs in control, ownership,
inspiration and following generated suggestions. Its scope is layout authoring,
not a general multiplayer game or a being-continuity system.

Adopt an editable intermediate representation and reversible alternatives: people
should be able to manipulate the proposal rather than accept a finished black box.
A Holodeck package should expose its scene and rules, source and versions. Test
whether participants can correct a suggestion without restarting the creation.

Source: https://arxiv.org/html/2408.09382v1 sections3–6.

### 4. CreepyCoCreator? (CHI2025)

The inspected paper examines embodiment, incremental edits and highlighting in
VR co-creation. Crucially, its method is Wizard-of-Oz: artists prepared the AI
contributions; it is not evidence of a working autonomous generative collaborator.
Embodiment and visualization affected users' perceptions; highlighting did not
universally improve predictability/partnership. The latest abstract revision is
v3,February21,2025; detailed method inspection usedv1, with that distinction retained.

Adopt evaluation of agency and understandable consequences rather than assume an
avatar or outline proves collaboration. Allow undo and negotiation. Do not
replace the daemon's true participation with timed animation or canned speech.

Sources: https://arxiv.org/html/2502.03069v1 ; https://arxiv.org/abs/2502.03069 .

### 5. Ubiq-Genie (2023 framework, current source inspected)

Ubiq-Genie is an open-source social-XR architecture with Unity clients, a Node
application controller, reusable service controllers and replaceable providers.
Its samples include multi-user conversational agents, transcription and generated
textures with voice/ray selection. Current README targets Unity6 and Node20+, not
necessarily the versions used by the original paper. Apache2 source and real
service boundaries make it a closer architectural reference than a render demo.

Adopt per-participant utterance ownership, shared scene events and replaceable
AI/voice services. Networked human–AI presence needs deliberate conversational
routing, not one global prompt for every visitor. Existing native companion and
voice services should be adapted before introducing another being/chat history.

Sources: https://ubiq.online/blog/integrating-generative-ai-into-social-vr-with-the-ubiq-genie-framework/
; https://github.com/UCL-VR/ubiq-genie ; Node/README.md.

### 6. CraftAssist (2019 historical research)

CraftAssist offers an open Minecraft assistant framework for tasks expressed in
dialogue, with memory, world entities and recorded interactions. Its original
work is historical and its repository is not a guarantee of current Minecraft
compatibility. Its value is the relationship between language, world references,
action and memory rather than its old deployment instructions.

Adopt stable world entities, action results, reference resolution and correction.
An action must be checked against world outcomes. Full situated activity requires
more than a selected block ID: retain who is doing what, event ordering and the
shared task. Compare a grounded observation with screenshot-only input without
assuming either modality alone is sufficient.

Sources: https://github.com/facebookresearch/craftassist ;
https://arxiv.org/abs/1907.08584 .

### 7. SIMA2 (DeepMind research announcement)

The official research page describes a Gemini-based agent that reasons and acts
in3D virtual worlds, including research with generated environments. It is a
research demonstration, not an established downloadable drop-in companion for
our runtime or an entitlement supplied by a consumer plan.

Useful contrast: embodied actions and generalization across worlds differ from
editable persistent co-creation and integration with one continuing daimon.
Holodeck can provide explicit structured perception/actions now while retaining
visual/audio context; it need not first reproduce a general pixel-control agent.

Source: https://deepmind.google/blog/sima-2-an-agent-that-plays-reasons-and-learns-with-you-in-virtual-3d-worlds/ .

## Social creation platforms and game/runtime patterns

### 8. Resonite / ProtoFlux

Official documentation presents in-world node-based programming and tools for
creating behavior inside shared VR spaces. This directly informs expressive
freedom: the environment should contain ways to inspect and change its workings.
It does not establish a portable AI-agent API or self-hosted Web/mobile runtime
matching our requirements. Evaluate as a design precedent, not an unexamined
platform migration.

Sources: https://wiki.resonite.com/ProtoFlux ;
https://wiki.resonite.com/World_Creation_Hub .

### 9. Croquet Microverse

Microverse exposes collaborative web world building and live behavior programming.
Its source/assets are Apache2 according to the inspected README; deployment beyond
local development needs its platform/API-key arrangement. Shared deterministic
simulation/replicated model and local presentation is a relevant alternative to
one authoritative room server. Network service dependence and behavior-edit
compatibility remain concrete adoption costs; open source does not imply that
all service deployment is already available in our infrastructure.

Sources: https://github.com/croquet/microverse ; docs/Tutorial.md and Avatar.md.

### 10. Roblox client–server and Minecraft content packages

Roblox documents an authoritative server maintaining shared game state; clients
render and replicate permitted state. Minecraft's official content documentation
separates behavior/resource packs, manifest dependencies and script API versions.
These are proven product patterns, not evidence that Holodeck can simply import
arbitrary Roblox or Minecraft games. Names, licenses, assets and runtime APIs differ.

Adopt content packages distinct from the platform, versioned dependencies,
server-validated actions, persistent creations distinct from ephemeral movement,
and explicit published-version/session transitions. Borrow familiar controls;
do not claim binary content compatibility or require proprietary accounts.

Sources: https://create.roblox.com/docs/projects/client-server ;
https://learn.microsoft.com/en-us/minecraft/creator/documents/scripting/introduction?view=minecraft-bedrock-stable
; https://learn.microsoft.com/en-us/minecraft/creator/documents/scripting/versioning?view=minecraft-bedrock-stable .

### 11. MML, Three.js, Babylon.js and Godot

MML's web3D experience already separates high-frequency user presence from
Networked DOM content state. Its source includes virtual joystick/jump and an
extensible authenticator. Babylon.js has integrated HTMLMesh and rendering tools;
its DOM path does not establish native/XR support. Godot provides native scene,
physics and authority-based multiplayer mechanisms, with different web/export
constraints. These libraries are reusable candidates, not equivalent complete
co-creation products.

The decision must turn on the first real experience: art/movement, shared
situation, package loading, action validation, native companion context and
PC/mobile use. A thin isolated Three.js scene can validate the semantic runtime
without pretending we have adopted MML's entire framework. Any departure from
reusing MML networking must have a specific integration/scope reason, not habit.

Sources: https://mml.io/3d-web-experience ; https://github.com/mml-io/3d-web-experience
; https://doc.babylonjs.com/addons/htmlMesh/
; https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html .

### 12. Scenario3D OS and generated-world systems

The prior pinned Scenario audit retains expert-tool families and hosted asset
production. Scene assets, splats and meshes can be useful production inputs.
They do not by themselves supply situated participation, network authority,
continuing companion identity or versioned game state. Keep providers optional
and compare cost per accepted asset, not promotional single-generation price.
Do not make photorealistic generation a prerequisite for a beautiful efficient
stylized world. The earlier launch video was unavailable; no visual fidelity
comparison with it is claimed.

Source: https://github.com/scenario-labs/skills/tree/f29bf06ab89088695ed3431ac99d20a090441a2f .

## Synthesis: proposed Holodeck architecture

1. A shared authoritative situation model: stable entities, participants, place,
   world time, current activity, semantic events and versioned content. Extensible
   context, not an exhaustive ontology or a camera-only transcript.
2. Separate low-latency simulation/presence from bounded conversational decisions.
   Each view renders smoothly; AI does not run every animation frame.
3. Situated observation adapter: what the actor can perceive, recent relevant
   events and activity, references and uncertainty. Store event-time references;
   do not replace what was seen with later state or leak another person's private
   attention/history. Structured and visual evidence complement each other.
4. Action adapter: typed, actor-attributed, server-validated operations with expected
   revisions, bounds and observed results. Multiple writers require ordering and
   conflict repair. A model proposal is not an observed action.
5. Creation package: immutable source/assets/rules/schema edition; independent live
   session/save state; explicit capabilities and stable release selection. Start
   with supported declarative behavior and retain an extension boundary.
6. Companion/native adapter: existing being and conversation, speech, chosen
   projection and actual attention state; shared utterance audience differs from
   private paired conversation. Holodeck is an Avatar surface, not a new being.
7. Shared identity/audience and established publication/review services. Reuse
   their canonical identities and stable links, rather than make a parallel release
   registry. Prototype persistence must be explicitly named as prototype until
   that adapter is integrated.
8. Bounded media/telemetry and actual physical-source adapters later. Intention,
   simulation, observation and interpretation remain distinguishable.

## Initial experiments and acceptance

A. Two humans and an actual daimon jointly build/operate a short cooperative
bridge/light mechanism, respond to an event, discuss what happened and modify
an element. Exercise 'this' ambiguity, simultaneous speakers, different viewpoints,
earlier events and resume after reconnect. Inspect actual native context/action
and human understanding separately.
B. Load a first bounded package, then a successor draft; current visitors keep a
stable edition until deliberate transition. Reopen a pinned past edition and
preserve source/current permissions.
C. Profile a polished small stylized place on desktop and selected physical
mobile device; measure navigation, responsiveness, loading, frame time and thermal
behavior, not screenshot quality alone. Future WebXR readiness is distinct from
headset acceptance.
D. Test rejection/recovery: stale action, unauthorized actor/source, incomplete
package, bounded rate/storage, disconnected native companion and failed change.
Errors remain product-readable; detailed diagnostics stay in a technical area.

MVP implementation must declare achieved coverage. A browser foundation with two
synchronized clients and a real author/API action can be useful progress, but
must not be called completed situated human–AI collaboration until native uptake
and meaningful joint activity have been observed. A user-selected Avatar-default
direction does not authorize silently replacing current active conversations.

## Open questions and next work

Current native Avatar external-context/action contract, supported shared HTTP
streaming transport, service placement and audience need receiving inspection.
The playable-room experiment should discriminate runtime choices before scaling.
The closer literature favors usable intermediate changes and understandable
agency; no inspected source proves that an avatar alone solves shared experience.
The plan and code review must challenge this synthesis, especially context
freshness, state authority, per-human identity and session/version transitions.
